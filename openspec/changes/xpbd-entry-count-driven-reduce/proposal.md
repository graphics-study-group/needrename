## Why

Every per-iteration step of the XPBD reduction path is sized by the contact entry **capacity**, which is a worst-case bound (`2 * min(all_pairs * 5, max_contact_points)` — the narrow phase can emit up to 5 manifold points per candidate pair), and not by the number of contacts that actually exist. The per-iteration scratch clear writes `7 * capacity` elements, and `SumByKey`'s level-0 gather reads one value per entry per channel — `7` separate cache-line touches per entry, since the channels are capacity-strided planes, not adjacent — for every entry of the capacity regardless of how many are real. For a 200-shape scene that is an estimated **~890 MB/frame** of clear + reduce traffic, of which typically ~1% is real data. The radix sort is a smaller matter: its histogram and scatter passes already guard on the pair count before any load, so what it wastes is dispatch geometry — `4 passes x 3 sub-dispatches x ceil(capacity / 64)` workgroups (roughly 3,700 for a 200-shape scene) that return immediately — rather than the same order of memory traffic. Measured against the pre-change float-atomic solver — whose cost was O(actual contacts) — the clear and reduce traffic is the dominant regression the scatter-plus-reduction design introduced.

The same capacity is also baked into the lifetime of the GPU algorithm objects: `RadixSort` and `SumByKey` take their geometry as constructor parameters and cannot be resized in place, so any geometry change forces a destroy-and-rebuild. That rebuild path is exactly where the stale-capacity bug fixed at the end of `remove-float-atomics` lived.

## What Changes

- **Two lengths, not one.** Every `SumByKey` level is bounded by two independent numbers. The **level element count** is the length of the array the level reads — `R_0 = capacity` at level 0, `R_i` above — and is a pure function of the capacity, so the CPU computes the whole chain. It alone defines the element-index bound, the per-block real extent that run classification uses, the record-region partition, the per-level dispatch counts and the level-0 channel stride. The **entry count** bounds **data extent only**: at level 0, no value is read for an element at or beyond it. It cannot replace the level element count, because the workgroup count must stay `ceil(capacity / 256)` and the per-element index mapping and the level-0 channel stride must stay consistent with the array they address.
- **The entry count travels in a binding.** It is produced on the GPU, so the host cannot put it in a push constant: `SumByKey::Record` binds the caller's entry-count buffer and the shader reads it at execution time, exactly as the radix sort already does with its pair count. The push-constant block is unchanged. The count is read only in gather mode, which only level 0 uses: a deeper level's input is the record region the previous level just wrote and is entirely valid.
- **⚠ Level-0 dispatch stays capacity-derived.** Level 0 always dispatches `ceil(capacity / 256)` workgroups and reads its input as a `capacity`-element array, so the record chain is rewritten in full every call. Sizing level 0's dispatch — or its array bound — by the entry count leaves holes in the record region that the next level reads as stale records (phantom partials), and makes the blocks that hold real data misclassify their last partial run.
- **Counted clear.** The per-iteration scratch clear becomes count-bounded instead of always writing `7 * capacity` elements, via a new counted clear shader that reads the count from a buffer. Its workgroup count stays capacity-derived for the same reason; only the writes follow the count. The reduce already only reads the values of entries below the count, so limiting the clear to the same range is sufficient.
- **Entry-count publication.** The contact entry pass publishes `min(2 * collision_count, capacity)` into its count buffer itself, since the collision count is GPU-produced in the same substep. Hinge and fixed counts are CPU-known and stay host-written, but change from the group **capacity** (`4 * max(1, joint_count)`) to the exact joint slot count (`4 * joint_count`) — otherwise the `joint_count == 0` case leaves slots the entry pass could not mark `INVALID` inside the array the reduction reads.
- **Geometry-free algorithm objects.** `RadixSort` loses `max_elem_count`; `SumByKey` loses its `max_entries` / `max_key_value` / `num_channels` members and their accessors. Both become stateless with respect to geometry and are shared as a single instance, and the solver's `EnsureSortAndSum` rebuild machinery is deleted — which makes the stale-capacity bug class unrepresentable rather than fixed.
- **Validation moves per call.** Both `Record` implementations validate their per-call capacity against the bound buffers' sizes (`ComputeBuffer::GetSize()`) instead of against a construction-time bound, so removing the stored geometry does not remove the out-of-bounds guard.
- **Deliberately unchanged:** Scheme A (the entry passes still write every slot in `[0, capacity)` — that write keeps every slot's key well-defined for the sort and for run classification, and its spec contract stays intact), the `max(1, ...)` capacity clamp that keeps `capacity == 0` out of the picture, the three-separate-reduce-group structure, the per-iteration barrier/recording order, and the reduction algorithm itself (this change alters which elements are read, never how a block reduces them).
- **Stepwise commits.** A pure rename commit (buffer names currently mislead: `pairs_a`/`pairs_b` imply two live arrays, the "scratch" holds the real contribution values while "records" is algorithm-internal), then the algorithm API change, then the solver wiring and tests.

## Capabilities

### New Capabilities

None. This change refines the behavior of capabilities introduced by the still-unarchived `remove-float-atomics` change and of three capabilities already in the main specs.

### Modified Capabilities

- `gpu-sum-by-key`: `Record` takes a per-call capacity plus an entry-count buffer; the constructor no longer takes geometry; the level element count stays the capacity at level 0 and governs the element-index bound, the run classification and the dispatch counts, while the entry count governs only which values are read; level-0 dispatch and the record-chain write stay capacity-derived; `GetNumLevels` / `GetRequiredRecordsBytes` become call-time helpers rather than instance geometry.
- `gpu-radix-sort`: `max_elem_count` is removed from construction and from the class's stored state; the out-of-range guard moves to a per-call check against the bound buffers.
- `xpbd-contact-solve`: the contact entry pass additionally publishes the entry count and the joint counts become the exact joint slot count; the per-iteration scratch clear and the reduction are bounded by that count instead of the capacity; the reduce reads only the values of entries below the count.
- `physics-gpu-shaders`: the solver's loaded-shader inventory gains the counted clear pass.

## Impact

- `engine/Physics/gpu_algorithm/SumByKey.h/.cpp` — constructor, `Record` signature, geometry computed per call, entry-count buffer binding, accessors removed.
- `engine/Physics/gpu_algorithm/RadixSort.h/.cpp` — `max_elem_count` removed, per-call buffer-size validation.
- `engine/Physics/shader/algorithm/sum_by_key.comp` — entry-count binding, value reads bounded by the count in gather mode, the two lengths documented; the push-constant block is unchanged.
- `engine/Physics/shader/solver/XPBDSolver/` — new counted clear shader; `entries/contact_entries.comp` publishes the entry count.
- `engine/Physics/Solver/XPBDGpuSolver.cpp` — single `RadixSort` / `SumByKey` instance, `EnsureSortAndSum` deleted, per-call geometry, count ownership (including the joint counts becoming the exact joint slot count), counted clears.
- `test/engine/headless/gpu_sum_by_key_test.cpp`, `test/engine/headless/gpu_radix_primary_test.cpp` — signature and contract changes, plus new cases for an entry count below the capacity with a garbage tail (on a 256-boundary and off it, and with the count at or below 256 while the capacity is large), a zero count, and an identity case where the count equals the capacity.
- New coverage for the capacity-change path (a headless `PhysicsScene` + `XpbdGpuSolver` harness that can change the shape/joint count between steps). This is the gap recorded as task 8.5 in `remove-float-atomics`; it is promoted to a required verification here because capacity changes stop being an edge case and become the normal per-call path. It is also the plan's largest unknown — if the fixture is expensive to build it should be split into its own change rather than block the algorithm and solver commits.
- **Ordering dependency:** this change modifies `gpu-sum-by-key`, whose requirements currently exist only inside the unarchived `remove-float-atomics` change. The two changes must be archived in order (`remove-float-atomics` first) for the delta to apply.
- **Owned elsewhere (explicitly out of scope):** the descriptor-set cache grows without bound when bound `(buffer, offset, size)` combinations change, and the solver's buffers are reallocated whenever the capacity changes. Both are being tracked as a separate issue (a planned redesign of the compute shader and binding layer). Note the two-sided interaction: this change removes the instance rebuild, so a capacity change no longer destroys the object holding the descriptor-set cache; against that, one shared instance with per-call bindings puts every distinct triple of a frame, plus one entry-count binding per level, into that single cache. No correctness or performance claim here depends on that issue being fixed.
- **Follow-on work identified but not done:** the radix sort's dispatch is still capacity-derived. Its histogram and scatter passes already guard on the count before any load, so its behaviour needs no change here, but a small contact count with a large capacity still pays `4 x 3 x ceil(capacity / 64)` empty workgroups. Shrinking that needs indirect dispatch. Separately, the reduction's block-internal sum is a run-local linear scan; replacing it with a segmented log-depth reduction is its own change with its own measurement.
- No public API breaks; every affected buffer, shader and algorithm entry point is solver-internal or a `gpu_algorithm` class used only by the solver.
